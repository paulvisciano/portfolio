Local TTS on 16 GB — the voice quality gap

Open WebUI talks to Bonsai. Whisper already handles speech-to-text. The remaining hard problem is the voice that talks back — and why "it works" is not the same as "it sounds human" on a 16 GB laptop.

Knowledge Graph is a private spatial canvas — photos, conversations, and time on a machine you own. The project has been building its own chat backend from scratch: streaming, retries, auth, audio plumbing, all hand-rolled. Today that stopped. The decision was to replace the entire custom chat stack with Open WebUI — same SvelteKit frontend language, same FastAPI backend, OpenAI-compatible model connections, built-in Whisper, a real tool and RAG layer. Everything the custom code was rebuilding by hand, poorly, already existed. Pointing it at the existing Bonsai-27B llama.cpp server was almost out of the box.

The model layer worked on the first try. Whisper handled speech-to-text out of the box. Chat streamed. The tools that were supposed to take weeks were there in an afternoon. The part that was supposed to be easy was easy. Then came the voice.

TTS options that fit 16 GB

The 16 GB budget is unforgiving. Bonsai-27B already claims roughly four gigabytes of weights. Whisper is resident. Open WebUI's backend and frontend are up. Brave, VS Code, and a coding agent that spikes under load take the rest. There is no spare room for a second large model — that is not a soft limit, it is the wall.

That is not a hypothetical. This is the machine right now, while writing this — an M2 Pro with 16 GB, running the full stack alongside a browser and an editor:

This is the normal state. A user does not close their browser to talk to their AI. The constraint is not the spec sheet — it is the machine you actually use, with everything open, every day. Any TTS engine that wants a second large model on top of this hits the wall. That is why the engine choice matters, and why "it runs" on a clean machine is a lie.

On paper, Kokoro JS is the right starting point. Open WebUI ships with it as the default local TTS — the 82M model running entirely in the browser, on the client. No server round-trip, no Python process, no extra RAM on the backend. In practice the default voice did not land. It was usable and fast, but it still sounded like a system voice: clear enough to understand, not natural enough to live with for long sessions. Latency was solved; presence was not.

Piper was the next try. It is fast, CPU-friendly, and designed for exactly this class of machine. Response time was excellent. The popular Lessac / Leesac voices were intelligible and stable, but still synthetic in a way you notice within a few sentences. Speed was solved. Naturalness was not.

Coqui TTS (XTTS-v2) was the heavier attempt — roughly 470M parameters, around 5 GB of RAM during model loading, and another 2 GB of VRAM on top. On a machine already running Bonsai, Whisper, Open WebUI, Brave, VS Code, and a coding agent, that is not a soft limit; it is the wall.

Bark was worse. A generative model that wants roughly 12 GB of VRAM with all three sub-models loaded, or 8 GB with the small flag, or 2 GB only by offloading to CPU where it crawls. A Bark experiment ended in a hard restart.

The fix was not another engine. It was running the same Kokoro-82M on the server instead of in the browser — a Python pipeline wired into Open WebUI as a first-class local engine. Same 82M weights, same model class, but the af_heart voice through the server pipeline lands as a real voice instead of a system voice. Natural enough to live with for long sessions. Latency was already solved; presence was not. Running it server-side closed that gap.

Why the voice is still the bottleneck

A voice you do not trust is a voice you mute. That is the whole problem. The model can reason, the transcription can be perfect, the latency can be instant — if the voice sounds synthetic, the conversation never starts. People do not talk to tools. They talk to voices that sound like they belong to someone.

This is not aesthetics. A synthetic voice triggers a specific kind of fatigue: you can understand every word, and you still want it to stop inside a minute. The brain treats natural speech as signal and synthetic speech as noise. Run a system voice for ten minutes and the instinct is to reach for the mute button, not to keep talking. That is the gap between "it works" and "it is used," and it is the gap that matters for a product you actually live with.

Frontier models get this right because they spend the compute. A 16 GB laptop does not have that room. Local LLM inference has improved faster than local TTS quality at the same memory budget — a 1-bit 27B model can reason and tool-call inside a few gigabytes of weights, but a voice that does not sound like a 2018 assistant still wants either more compute, more VRAM, or a cloud API. Until today.

The surprise was not a new engine. It was the same 82M Kokoro model run server-side instead of in-browser. Same weights, same class, noticeably different voice. The browser default was a system voice. The server pipeline with af_heart was a voice you can live with — natural enough that the instinct to mute never triggered. That is the bar: not "intelligible," but "kept on."

For Knowledge Graph and the wider Sci-Fi Labs stack, the design constraint stays the same: everything that touches private memory stays on hardware you control. Cloud TTS is a temporary convenience, not the architecture. The honest state today is: chat works, STT works, TTS works — once the same model is on the right side of the browser.

What changed in the Open WebUI fork

Alongside the evaluation, Kokoro was wired in as a first-class local engine option: config keys, admin UI, pipeline load, voice allowlist, and MP3 output that browsers actually play. A few integration bugs showed up along the way — wrong MIME types when WAV bytes were written under an .mp3 path, stale Piper voice names in the payload causing Hugging Face 404s, and sequential sentence synthesis that delayed the first audible chunk. Those are fixed. Parallel sentence requests cut perceived latency to time-to-first-sentence instead of the sum of every sentence.

That work is useful whether the long-term surface stays Open WebUI or the Knowledge Graph frontend keeps calling the same APIs. The point of the day was not to adopt a chatbot UI forever. It was to stop rebuilding streaming, retries, auth, and audio plumbing by hand.
