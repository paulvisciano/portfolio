Local TTS on 16 GB — the voice quality gap

Open WebUI talks to Bonsai. Whisper already handles speech-to-text. The remaining hard problem is the voice that talks back — and why “it works” is not the same as “it sounds human” on a 16 GB laptop.

Most of the day went into replacing custom chat and message plumbing with something that already works. The choice was Open WebUI — same SvelteKit surface language as the Knowledge Graph frontend, FastAPI backend, OpenAI-compatible model connections, built-in Whisper, and a real tool and RAG layer. Pointing it at the existing Bonsai-27B llama.cpp server was almost out of the box.

That part was the easy win. The rest of the day was voice.

What worked without a fight

Open WebUI’s connection model is straightforward. The Bonsai llama-server already exposes an OpenAI-compatible /v1 endpoint. Add the base URL, leave the key blank or placeholder, and the model appears in the UI. Streaming works. The first real message went through with the full system context and came back clean.

Speech-to-text was already solved for this machine. Open WebUI ships with local Whisper. That matched what the Knowledge Graph stack was already using, so the STT path did not need a redesign. Voice mode is there: talk, get a reply, hear it spoken, mic re-arms.

One gotcha showed up immediately. Open WebUI enables a large set of tools by default — twenty-plus in a fresh install. The system prompt that describes all of them is huge. On a small local model that cost was visible: responses crawled. Turning the tools off dropped latency to near-instant. The model was fine; the prompt was the tax.

The model layer and the transcription layer were ready. The voice that speaks the answer was not.

TTS options that fit 16 GB

Open WebUI’s default local TTS path is Kokoro (via Kokoro JS / related local engines). Kokoro-82M is light, OpenAI-compatible in several wrappers, and ranked high on open TTS boards for its size. On paper it is the right class of model for this hardware.

In practice the default voice did not land. It was usable and fast, but it still sounded like a system voice — clear enough to understand, not natural enough to live with for long sessions. That is the recurring gap: latency is solved; presence is not.

Heavier neural TTS options were tried next. Several of them simply ran the machine out of memory. With Bonsai already loaded, Whisper resident, Open WebUI’s backend and frontend up, plus Brave, VS Code, and a coding agent that spikes under load, 16 GB has no spare room for a second large model. A few experiments ended in a hard restart. That is not a soft limit; it is the wall.

Piper TTS is the pragmatic fallback. It is fast, CPU-friendly, and designed for exactly this class of machine. Response time is excellent. The popular voices (including the widely used Lessac / Leesac family) are intelligible and stable. They are also still synthetic in a way you notice within a few sentences. Speed is solved. Naturalness is not.

Why the voice is still the bottleneck

Local LLM inference has improved faster than local TTS quality at the same memory budget. A 1-bit 27B model can reason and tool-call inside a few gigabytes of weights. A voice that does not sound like a 2018 assistant still wants either more compute, more VRAM, or a cloud API.

That mismatch matters for any product that wants spoken interaction without sending audio off-device. Whisper already keeps transcription local. The missing piece is a TTS path that is both light enough to share the machine with the LLM and good enough that people do not mute it after a minute.

For Knowledge Graph and the wider Sci-Fi Labs stack, the design constraint stays the same: everything that touches private memory stays on hardware you control. Cloud TTS is a temporary convenience, not the architecture. The honest state today is: chat works, STT works, TTS is good enough to demo and not yet good enough to trust for long daily use.

What changed in the Open WebUI fork

Alongside the evaluation, Kokoro was wired in as a first-class local engine option: config keys, admin UI, pipeline load, voice allowlist, and MP3 output that browsers actually play. A few integration bugs showed up along the way — wrong MIME types when WAV bytes were written under an .mp3 path, stale Piper voice names in the payload causing Hugging Face 404s, and sequential sentence synthesis that delayed the first audible chunk. Those are fixed in the integration notes. Parallel sentence requests cut perceived latency to time-to-first-sentence instead of the sum of every sentence.

That work is useful whether the long-term surface stays Open WebUI or the Knowledge Graph frontend keeps calling the same APIs. The point of the day was not to adopt a chatbot UI forever. It was to stop rebuilding streaming, retries, auth, and audio plumbing by hand.
